# Slice A IAM, Model, Capability and Web SiteContext Phase Roadmap

> **Document type:** Reviewed phase roadmap, not direct `executing-plans` input. Before a lane starts, its next milestone MUST be expanded into a separately reviewed JIT implementation cut with exact files, actual RED test/code, self-contained commands and one precise commit; workers never invent omitted code from this roadmap.

**Goal:** Stand up three independent capability repositories that own the complete user security context, Model selection and the explicit empty Capability snapshot used by Slice A. SiteContext selection stays in the Web/BFF server boundary.

**Architecture:** IAM, Model and Capability each start from a history-preserving `kokoro-platform` subtree seed, consume Root-generated Protobuf and an owner-scoped PostgreSQL schema, and expose a narrow RPC boundary. Web/BFF resolves an allowlisted Host against its server-side SiteContext environment binding and supplies the selected `site_id`; IAM does not select a Site and only validates the database-backed active Site/Organization/AuthSession chain. Existing domain algorithms and behavior tests are moved intact where valid; MySQL/Mongo repositories and child migrations are replaced with PostgreSQL adapters.

**Tech Stack:** Node.js 22+, TypeScript 5, pnpm 11, Prisma Client PostgreSQL, `pg`, Connect RPC, Protobuf-ES, Vitest, JOSE.

## Global Constraints

- Repositories are separate Git roots: `/tmp/kokoro-iam-slice-a`, `/tmp/kokoro-model-slice-a`, `/tmp/kokoro-capability-slice-a`.
- Each child `prisma/schema.prisma` is generated by Root and contains only owner tables; the child exposes `db:generate` and `prisma:validate`, never migrate/push/pull/reset.
- Preserve current User magic-link/refresh/JWKS behavior and Model routing/fallback behavior; Slice A health is an explicit `unknown` state, not active probing.
- IAM is the only owner of Principal, User, Identity, Contact, Authentication session, Organization, Membership, Role and Permission.
- Slice A does not install Invite, ServiceAccount, Credential, OperatorSiteRole, Site Brand/Feature, Skill/MCP or Capability snapshot items.
- Capability returns a persisted empty snapshot header; it does not construct Hub Mongo, S3, keyring or MCP clients.
- Model returns immutable `ModelSelection`; it never proxies model invocation or records usage.
- TypeScript servers register generated handlers on HTTP/2 with Connect and gRPC protocols enabled. Model/Capability integration tests invoke the same methods once with a TS Connect client and once with the generated Python grpcio client used by Agent.
- Listeners are fixed to IAM 7202, Model 7203 and Capability 7204 with exact `/healthz` and `/readyz`. IAM Authentication methods accept only Web, IAM Authorization accepts only Chat, and JWKS is public; Model/Capability accept only Agent. Interceptors bind exact service/method → caller before request decoding, so possession of another valid workload token does not widen authority.
- The runtime child allowlist is exactly IAM, Model, Capability, Chat, Agent and Web. `site_site`/`site_domain` remain Root-owned DDL facts in IAM's owner scope; the local Root fixture provisions the reviewed Site rows, and IAM fail-closes unless the selected Site and all session/organization bindings are active.
- Frozen compatibility-artifact retirement is defined only by the structured retirement boundary in the master roadmap; this plan does not alter that authority.

**JIT cut requirement 4 — Implement one login transaction**

At startup, IAM idempotently seeds the five frozen permission keys as `active` and refuses readiness if the catalog differs. `RequestMagicLink` first locks and validates the Web-selected active `site_site` row; it does not resolve Host or select a Site. `ConsumeMagicLink` locks the same Site, the link row and receipt, then in one serializable transaction creates or resolves Contact → Identity → Principal → User → personal Organization → owner Membership → organization Role `personal_owner` → five RolePermission rows → MembershipRole → AuthSession → SecurityEvent. The AuthSession stores the same Site/Organization binding and immutable `family_generation`; it never derives Principal ID from email. An authorization integration test disables one permission without deleting its role bindings and proves the corresponding command is denied.

```ts
export type LoginResult = {
  principalId: string
  siteId: string
  organizationId: string
  authSessionId: string
  accessToken: string
  refreshToken: string
}
```


`FixtureFileMagicLinkMailer` is test-only and is selected only when `KOKORO_RUNTIME_MODE=fixture`. It requires a
pre-created mode-0700, non-symlink directory from `KOKORO_MAGIC_LINK_FIXTURE_DIR`, writes bounded
`{requestId,normalizedEmail,token,expiresAt}` JSON through `${requestId}.json.tmp`, fsyncs, atomically renames to
`${requestId}.json` mode 0600, and never logs the token. Production mode rejects the fixture variable/adapter and
requires the existing real mailer. Its test proves atomic visibility, exact schema, permissions, symlink rejection,
path traversal rejection and no partial file after injected failure.

Signing happens after commit. The refresh token is deterministically derived as `base64url(HMAC-SHA256(refresh_derivation_key, "kokoro.refresh.v1\n" + auth_session_id + "\n" + family_generation))`; SQL stores only its SHA-256 hash. Slice A mounts one IAM-only derivation key and does not rotate it while any AuthSession or command receipt derived from it remains within retention. Key-ring rotation is a later schema cut that must first add a non-secret derivation-key ID to AuthSession and retain every referenced key through session/receipt expiry; an `active/previous` two-key shortcut is explicitly rejected. If the first response is lost or signing fails after commit, replaying the same command/digest rereads the same AuthSession and re-derives the same refresh token without creating a second session; the access JWT may be freshly signed for that same session. Tests drop the first response, retry, assert identical AuthSession/refresh token and one row, then drift the digest and assert conflict; startup/restart with the same mounted key preserves replay, while changing the key with live retained sessions fails readiness.

**JIT cut requirement 5 — Implement refresh-family locking and IAM RPC**

`RequestMagicLink` preserves existence-hiding and current rate limits. `RefreshSession` locks the active family row, creates one successor with `family_generation+1`, marks the old row rotated and writes SecurityEvent in the same transaction; the successor raw token is re-derivable from that immutable generation while SQL retains only its hash. `Logout` revokes the family; `GetSession` returns the verified context. Access JWTs follow the machine authority exactly: RS256 + active `kid`/`typ=JWT`, issuer `kokoro-iam`, audience `kokoro-user-backend`, principal/Site/Organization/AuthSession UUID claims, 900-second maximum TTL and no `nbf`. `Authorize` revalidates all cryptographic/time claims, loads the active AuthSession and proves its principal/Site/Organization binding before checking active Membership/Role/Permission rows and returning `PrincipalContext`; free-form identity headers and caller-supplied permission sets are rejected. Tests cover wrong alg/kid/signature/issuer/audience/organization, expired/future-issued JWT, inactive session, disabled membership and disabled permission. Startup rejects missing, short, symlinked or world-readable refresh-derivation and JWT-signing key files before opening the listener.
