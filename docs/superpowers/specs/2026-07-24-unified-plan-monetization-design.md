# 统一「套餐(Plan)」货币化模型 — 技术方案

状态：草案待评审
日期：2026-07-24
缘起：现有货币化是三套机制（按量积分 + 一次性积分包 + 订阅）各建一半、还自相矛盾
（落地页"没有隐藏订阅" vs 设置页"订阅套餐"；"套餐"一词既指积分包又指订阅）。
根因：**先造了收钱的机器，没设计收钱的产品**。本方案把三者统一到一个抽象下。

> 设计理念参考行业收敛结论（订阅+预付积分共存、按来源定过期、权益与积分分层），但
> **本文所有选型论据只来自我们自己的约束**（做海外 / 个人暂无商户 / agent 产品 / 已有 credit 机器 / USD 价值化）。

---

## 0. 约束（论据来源）

- **做海外**：定价用 USD、按价值锚定，不用 ¥、不暴露 token/micros/成本。
- **个人暂无商户**：真周期扣款暂缺（mock/离线到账够用）→ 订阅生命周期必须能脱离真支付独立运行。
- **agent 产品**：消费点是 run（模型调用 + 工具），已有 hold/settle 计量。
- **已有机器**：credit ledger、hold/settle、积分包 seed、payment 域、subscription 域——**统一而非重建**。
- **未上线**：可按最优设计，不背历史兼容包袱（先扩展、后收缩的加法迁移即可）。

---

## 1. 一个抽象：一切皆「套餐 Plan」

账户能持有的每一种"offering"都是一个 Plan。免费、积分包、订阅是**类型**，不是并列的三套东西。

| 类型 | 价格 / 计费 | 授予 credits | 授予权益 | 有效期 |
|---|---|---|---|---|
| **免费 free** | 0 / 无 | **每日赠送额度**（进每日桶）+ 一次性欢迎 | 基础权益（基础模型、低并发） | 恒在（人人默认） |
| **积分包 credit_pack** | 一次性 USD | 固定积分，进**永久桶** | 无（纯充值） | 即时到账，**积分永久** |
| **订阅 subscription** | 按月 USD，周期从购买时刻起算 | 每月额度（周期桶）+ 可含更高每日赠送（每日桶） | **核心：解锁高级模型/更高并发/优先级/更低消耗倍率** | 周期内有效，到期失效/续费 |

> 「多种套餐」= Plan 目录多行：多档积分包 + 多档订阅（Basic/Pro/Max，各自 每日/每月额度 + 权益）+ 免费。
> 每档的"每日多少 / 每月多少 / 永久多少 / 什么权益"都是该 Plan 的属性。

**三者可同时并存**：账户 = 免费（底座）+ N 个积分包（永久积分）+ ≤1 个生效订阅（周期额度 + 权益）。

---

## 2. 拆开被缠在一起的三根轴（现设计烂的根因）

现有设计把下面三件事糊成一团。统一模型把它们**正交拆开**：

1. **货币（积分 credit）**：唯一可花的单位，run 处 hold/settle 计量。**已有，保留为底座。**
2. **授予（grant）**：积分怎么进余额——一次性（积分包→永久）/ 月度（订阅→周期）/ 每日（免费或订阅→每日）。
   → **三个桶：每日 / 周期 / 永久（按过期节奏分，见 §3）。**
3. **权益（entitlement）**：不可消耗的能力——模型档位、并发、速率/优先级、**消耗倍率**。
   → 这是订阅区别于"每月送积分"的灵魂；免费/订阅各档权益不同。

> 判据：把"能花多少"（credit）和"能用什么/多快/多便宜"（entitlement）分层，是订阅有存在价值的前提；
> 缠在一起就退化成"订阅=每月送积分"，留不住人。

---

## 3. 三个积分桶 + 消费顺序（钉死语义）

按"过期节奏"分三桶（这是唯一需要的区分，其余都是 Plan 属性）：

- **每日桶 daily**：每日赠送额度（免费档人人有；订阅档更高）。**每天重置、不结转**（use-or-lose，驱动每日回访）。
- **周期桶 period**：生效订阅的月度额度。**每月重置、不结转**（可选到期前提醒，绝不静默清零）。
- **永久桶 permanent**：积分包购买 + 一次性欢迎。**永不过期**（钱已收，长效资产/负债）。
- **余额 = 每日 + 周期 + 永久**；用户面分别显示（今日免费额度+重置倒计时 / 本月订阅额度 / 永久积分）。

**消费顺序：过期最快的先扣 —— 每日 → 周期 → 永久。**
判据：先花快过期的，用户永不白损失（护每日活跃 + 订阅复购 + 永久积分保值）。
与"产品以积分包为主打"不矛盾：**产品叙事**积分包是英雄品，**扣费顺序**按价值保护走，两回事。

> 关键统一：三桶只是**过期节奏不同**（日/月/永久），"每日多少、每月多少、永久多少"全是 Plan 的 grant 属性。
> 加一档套餐 = 目录加一行，不改扣费/桶逻辑。

---

## 4. 权益层（entitlement）

订阅生效时把一组权益投影到运行时，run 受理与计价读取：

- **模型档位准入**：免费=基础模型；订阅=解锁高级/更快模型（与 kokoro-model 的 label 档位挂钩）。
- **消耗倍率 multiplier**：订阅可享更低的每 run 积分消耗（如 0.8×）——比单纯送积分更有黏性。
- **并发 / 优先级**：订阅更高并发上限、队列优先（agent run 调度侧）。
- **配额 quota**：与现有 quota 机制对齐（订阅抬高月度上限）。

权益从"生效订阅 + 免费默认"解析出一份快照，run 受理时校验（模型准入）+ 计价时应用（倍率）。

---

## 5. 支付 / 订阅分层（你的"支付、订阅分开做"）

- **支付层（kokoro-payment）**：只管一次交易——积分包=一次性收款、订阅=周期收款。可换 provider（mock/离线/真网关）不影响上层。
- **订阅生命周期层（新，独立）**：激活→周期窗口→到期→续费→取消→宽限；周期起点=购买时刻；到期切回免费权益；月度额度刷新 job。**能在 mock/离线支付下独立跑**（满足无商户）。
- 两层都只向账户 Plan 状态 + credit grant 写入；**解耦**让"没有真网关"也能完整验证订阅逻辑。

---

## 5.5 卡密兑换渠道（第三条获取渠道，解"无商户"死结）

三条并列的**获取渠道**，全部汇入统一 credit 桶（互不替代）：
① 直接支付买积分包 → 永久桶；② 订阅 → 周期桶（+权益）；③ **卡密兑换 → 永久桶（积分加量包）**。

**卡密为什么关键**：**兑换不需要我方接支付网关**。批量生成卡密 → 经分销商 / 第三方市场（淘宝/Gumroad 等）/ 线下 卖 →
用户"输码即到账"。这正好绕开"个人无商户、做海外"接不了周期扣款的死结——**用卡密把积分包卖出去，零支付集成**。

**模型（并进 Plan）**：
- 卡密**绑定一个 credit_pack 型 Plan**（= 某"积分加量包"）——卡密是该 Plan 的**分发/发放通道**，不是新品类。
- **批次 batch**：`{绑定 plan, 数量, 过期, campaign/分销商标记}`——用于发行、追踪、对分销商归因营收。
- **一码 code**：随机不可猜、**一次性**、可过期；`{code_hash, batch, status: unused|redeemed, redeemed_by, redeemed_at}`（存 hash 不存明文）。
- **兑换流程**：输码 → 校验（存在/未用/未过期）→ **原子占用(CAS)** 标记 redeemed → grant 该包积分进永久桶 → 落 ledger（营收归因批次/分销商）。
- **安全**：随机长码、一次性 CAS、**兑换限频**（防撞库）、明文不落库（只存 hash）。
- **admin**：生成/作废批次、查兑换率、按批次/分销商看营收——纳入 §9 运营台。

> 判据：卡密 = credit_pack 的一条**零支付集成**分发通道，天然契合无商户/海外；与支付、订阅正交并存。

## 6. 时间型授予的实现：**懒 materialize，不用 cron 定时发放**

你问的每日赠送怎么实现——**懒加载（on-access 惰性刷新），不是定时任务批量发放**。每日桶、订阅月度桶都用同一套。

**为什么懒 > 定时 cron（逐条论据）：**
1. **规模**：定时发放要每天/每月写**所有**账户（含永远不回来的死号）→ 不 scale、纯浪费。懒加载只在账户**真来用时**才写，活跃即成本。
2. **无午夜惊群**：不制造零点写风暴。
3. **时区灵活**：按账户自己的"今天"算，不被单一 cron 时刻绑死。
4. **自愈幂等**：漏跑、宕机都无需补发——水位自校正。
5. **天然契合 use-or-lose**：是"当天首访重置"，不是"累计 N 天"——回来一天给一天，绝不堆 30 天。

**机制（钉死）：**
- 每账户存**水位**：`daily_reset_on`(日期) + `daily_micros`；`period_reset_on` + `period_micros`。
- 所有触碰余额的入口（run 受理 hold / 计费面读取 / 登录）先调 `ensureAllowancesFresh(account, now)`：
  - 若 `daily_reset_on < today(now)` → **条件写(CAS)** `daily_micros = plan.每日额度, daily_reset_on = today` WHERE 水位仍旧（并发只一个赢，其余看到已刷新）。
  - 若订阅生效且 `period_reset_on < 本周期起点` → 重置 `period_micros = plan.每月额度`。
- **重置(overwrite)非累加** → 回归 N 天只得一天额度。
- **日界**：V1 用 UTC（文档写明；账户本地时区留后续）。
- **race-safe**：水位 CAS，与现有"单 active run 准入"同一条件写纪律。

**ledger 口径**：每日/周期桶是**易逝状态，不逐条记账**（百万级惰性重置会把 ledger 撑爆）。
只有**永久桶的钱**（买包/退款）和**真实消费**（settle）进 ledger；每日刷新是状态重置、非财务事件。
用户面"今日免费 X、Y 小时后重置"由桶状态派生，不需每次赠送一条流水。

**推广**：订阅**到期**也懒判定（访问时 now>周期末且未续 → 落回免费权益）。**唯一**需要真调度器的是
"真周期扣款(payment)"——个人无商户下**本就延后**。→ **授予/权益零 cron；真扣款的调度留到接真网关。**

## 7. 数据模型（映射现有，加法为主）

- **Plan（新权威实体）**：`{id, name, type: free|credit_pack|subscription, price{amount,currency=USD}, billing: one_time|monthly|none, grant{credits, recurring}, entitlements{model_tier, multiplier, concurrency, priority, quota}, display}`。
  收编散在的积分包 seed + 定价规则到统一 Plan 目录。
- **AccountPlanState**：免费（恒）+ 已购积分包（流水）+ ≤1 生效订阅（周期/续费时刻/权益快照）。
- **CreditBalance**：`daily_micros + daily_reset_on + period_micros + period_reset_on + permanent_micros`。
  hold/settle 扩为**三桶 + 消费顺序（每日→周期→永久）+ 惰性刷新（§6）**。
- **Entitlements**：从生效订阅解析；run 受理校验 + 计价应用倍率。
- **复用**：credit ledger/hold/settle（扩三桶）、payment 交易层、subscription 域（重构进生命周期层）、pricing 规则（降为"成本地板 + 倍率输入"）、quota（订阅抬高）。

**迁移**：纯加法。现有积分→永久桶；新增每日桶 + 周期桶 + 权益 + Plan 目录 + 订阅生命周期。先扩展、不破坏。

---

## 8. 定价与价值化（USD，非 ¥ 成本加成）

- **对外**：USD 圆整价 + **价值锚定**（"500 积分 ≈ N 次生成 / N 次 agent run"），不暴露 micros/token/成本×倍率。
- **对内**：成本×margin 仍算，但只作**价格地板**（不亏本卖）+ 权益倍率输入；不再是对外定价口径。
- **积分包**：阶梯折扣（越大越省）；**订阅**：月费含额度 + 权益，主打"更便宜地用 + 用更好的"。

---

## 9. web / admin 重塑（业务模型理顺后才做）

- **定价页**：一条统一「套餐」阶梯 [免费]→[积分包 tiers]→[订阅 tiers]，卡片标「永久/每月」+「含权益」，USD 价值化。
- **设置·计费主页**：当前套餐 + 订阅状态/续费日 + 两桶余额（永久 / 本月额度含重置日）+ 买包 + 管订阅 + 用量流水。
- **营销**：修掉自相矛盾——不再写"没有隐藏订阅"；改诚实三态"免费起步 · 随时买永久积分包 · 或订阅拿月度额度+高级权益"。
- **admin**：从 CRUD 表升为 **Plan 目录治理（定义/定价/权益/启停）+ 运营看板**（MRR、订阅数、包收入、**积分负债**=未消耗永久积分、按模型消费、转化漏斗）。

## 10. 执行序（提案）

1. 本 spec 评审定稿 → 迁入 handbook 作权威。
2. credit 域：两桶 + 消费顺序（周期先扣）。
3. Plan 目录 + 收编积分包/免费/订阅为 Plan 类型。
4. 权益层 + run 受理/计价接入（模型准入 + 倍率）。
5. 订阅生命周期层（周期/续费/到期/月度刷新，mock 支付下可跑）。
6. web 定价页/设置页按统一套餐卡重塑（USD 价值化）。
7. admin Plan 治理 + 运营看板。

## 11. 待你确认的收口点（我已定，仅供纠偏，非开放问题）

1. **消费顺序**：周期桶优先→永久桶兜底（护用户价值）。← 我顶了你的"积分包优先"，理由见 §3。
2. **周期额度**：不结转 + 到期前提醒（透明）。
3. **订阅灵魂**：权益（模型/倍率/并发/优先级）为主 + 月度额度为辅。
4. **定价**：USD + 价值锚定，成本×margin 退为内部地板。
